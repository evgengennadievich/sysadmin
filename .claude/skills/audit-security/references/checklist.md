# Чек-лист security-аудита: обоснование каждого пункта

Документация для понимания «зачем». Каждый пункт чек-листа в `security-audit.sh`
имеет конкретный риск, который он закрывает.

Связанные документы:
- `knowledge/security-hardening.md` — базовое укрепление Ubuntu-сервера.
- `decisions/0010-local-images-latest-allowed.md` — почему локальные сборки могут
  быть `:latest`.

---

## Методологический принцип: у проверки три исхода, а не два

Введён 2026-07-29 после разбора ложных срабатываний на реальном аудите.

| исход | значение |
|---|---|
| **PASS** | проверка выполнена, нарушений нет |
| **WARN / FAIL** | проверка выполнена, найдено нарушение |
| **UNKNOWN** | **проверка не выполнена** — нет прав, нет каталога, нет утилиты |

**Почему это критично.** Проверяющая команда, которая упала, возвращает пустой вывод —
ровно как команда, которая отработала и ничего не нашла. Если не различать эти случаи,
скрипт превращает собственную неудачу в бодрый PASS.

Реальные примеры того прогона:

- права `.env` искались в `/opt/*`, а сервисы жили в `/srv/apps` — **не проверен ни один
  файл**, отчёт: «PASS, все `.env` mode 600»;
- `ufw status` без `sudo` отвечает «You need to be root» — отчёт: «FAIL, UFW неактивен»
  на сервере с полностью рабочим firewall;
- `ss` без прав возвращал пусто — отчёт: «PASS, наружу только 22/80/443».

**Ложный FAIL плох, но заметен** — его идут перепроверять. **Ложный PASS не заметен
вообще** и создаёт уверенность там, где проверки не происходило. Из двух ошибок вторая
дороже.

**Практическое правило.** Прежде чем трактовать пустой результат как «чисто», ответь:
сколько объектов проверка вообще увидела? Ноль найденных файлов — это не «все файлы в
порядке», это «проверять было нечего». Счётчик проверенного обязателен там, где вывод
может быть пустым по двум разным причинам.

### Дополнение 2026-07-29 (второй заход): кода возврата недостаточно

Первая редакция принципа предлагала опираться на код возврата команды. Проверка кода
на подставном сервере показала, что этого мало, и три проверки из четырёх новых
оказались сломаны именно здесь.

| ловушка | что происходит | к чему привело |
|---|---|---|
| `grep` возвращает 1, когда совпадений нет | это ответ «чисто», а не сбой; ту же единицу отдаёт `sudo -n` при отказе | ветка PASS у проверки NOPASSWD стала **недостижимой** — лучший исход системы показывался как UNKNOWN |
| конвейер отдаёт код последней команды | `getent group docker \| cut -d: -f4` возвращает код `cut`, то есть всегда 0 | отсутствие утилиты и обрыв связи давали **PASS «группа пуста»** — ложный PASS в новой проверке |
| `systemctl is-active` возвращает ненулевой код для неактивной службы | это ответ, а не сбой | пустой вывод при обрыве связи давал **FAIL «не запущен»** |
| `find` без root молча пропускает чужие каталоги | обход неполон, но код возврата об этом не говорит | **PASS «проверено N файлов, все 600»** при непроверенной части |

**Решение — маркер выполнения.** Команда уходит на сервер завёрнутой в `sh -c`, который
дописывает в вывод маркер, если действительно отработал. Признак «проверка состоялась» —
наличие маркера, а не код возврата. Завёртка именно в удалённый `sh -c` принципиальна:
при отказе `sudo` оболочка не запускается вовсе, и маркер физически не может появиться.

**Отдельный статус INFO.** Перечень правил UFW и список слушающих портов не имеют исхода
«хорошо/плохо» — оценка требует инвентаря, которого у скрипта нет. Считать их за
пройденные проверки значит завышать итоговую цифру: сводка «11 PASS» звучит как «11
проверок пройдено», хотя две из них ничего не проверяли. Та же болезнь, что и ложный
PASS, только на уровне сводки.

**Код возврата скрипта тоже несёт смысл:** `0` — чисто, `1` — есть FAIL, `3` — FAIL нет,
но часть проверок не выполнена. Прежде выход был `0` в обоих последних случаях, и
вызывающая сторона читала непроверенное как успех.

## Host scope

### 1. UFW активен + default deny incoming

**Риск без проверки:** на сервере публичный IP, любой порт по умолчанию доступен
из интернета. Если приложение случайно слушает на 0.0.0.0 (а не 127.0.0.1) — оно
открыто для атаки без firewall'а.

**Что должно быть:**
```bash
ufw status verbose
# Status: active
# Default: deny (incoming), allow (outgoing), disabled (routed)
```

**Почему `deny incoming` важнее всего:** на публичных VPS постоянно идёт сканирование
портов (SSH brute force, Redis 6379, MongoDB 27017). Default deny — защитный слой,
даже если приложение случайно публикуется наружу.

### 2. UFW allow только 22/80/443

**Риск:** если открыты дополнительные порты «для удобства» (8080, 5432, 6379) —
прямой target для атаки.

**Исключения, которые допустимы:**
- Кастомный SSH-порт (например, 2222 вместо 22) — задокументировать в `inventory/server.md`.
- Provider-level firewall на VPN/SSH — может открывать дополнительные порты для
  оператора, но не для всех.

### 3. SSH PasswordAuthentication no

**Риск:** SSH с паролями уязвим для brute-force. Даже с fail2ban, слабый пароль
ломается за часы перебором словарных вариантов.

**Почему ключи безопаснее:** ed25519 ключ — это эффективно 256-бит entropy,
brute-force невозможен в обозримое время. Пароли же — обычно < 64 бит entropy.

### 4. SSH PermitRootLogin не yes

**Риск:** root-логин = полный root доступ при компрометации. С `prohibit-password`
оператор должен SSH как обычный пользователь, потом sudo — двухэтапная защита.

**Допустимые значения:**
- `no` — root не может логиниться через SSH вообще.
- `prohibit-password` — root может только по ключу, без пароля.

`yes` — небезопасно.

### 5. fail2ban active + sshd jail

**Риск:** даже с ключами SSH, brute-force forçает запись в логи и тратит ресурсы
(fork SSH-сессии). fail2ban банит IP после N неудачных попыток.

**Что важно проверить:**
- `systemctl is-active fail2ban` → active
- `fail2ban-client status sshd` → отвечает (jail настроен, не просто демон работает)

### 6. unattended-upgrades без auto-reboot

**Риск без unattended-upgrades:** security-патчи приходят с задержкой («руки
не дошли»), уязвимости открыты дольше необходимого.

**Риск с auto-reboot включённым:** сервер ребутает себя в случайный момент
(обычно 2-3 ночи), это сюрприз для оператора, особенно если идут долгие задачи.

**Решение:** unattended-upgrades включён, но `Automatic-Reboot "false"`.
Оператор сам решает когда ребутнуть после kernel update.

### 7. Открытые внешние порты только 22/80/443

**Риск:** контейнер случайно публикует порт через `ports: - "5432:5432"` —
PostgreSQL открыт миру. UFW его не блокирует (Docker обходит UFW через iptables,
см. `knowledge/security-hardening.md`).

**Что проверять:** `ss -tlnp` и фильтр на 0.0.0.0 (а не 127.0.0.1). Все нестандартные
порты должны слушать на 127.0.0.1.

**Оговорка:** «нестандартный порт наружу» — не всегда дефект. Панель управления на
случайном порту и VPN-инбаунд на 443 — штатные конфигурации (см. рефлексы персоны
§3.8.5 и §3.8.8). Требование не «портов быть не должно», а «каждый порт наружу должен
быть в инвентаре и либо закрыт в UFW, либо открыт осознанно».

### 8. sudo: правила NOPASSWD (добавлено 2026-07-29)

**Риск:** `NOPASSWD: ALL` означает, что защита сервера держится ровно на одном барьере —
SSH-ключе. Компрометация ключа (украденный ноутбук, утёкший файл, доступ к незаблокированной
машине) даёт немедленный полный root, без второго рубежа и без паузы на размышление.

**Что проверять:** `sudo grep -rhE 'NOPASSWD' /etc/sudoers /etc/sudoers.d/`

**Почему это WARN, а не FAIL:** без `NOPASSWD` ломается автоматизация (плановые задачи,
диагностические прогоны агента), и оператор вынужден вводить пароль на каждую мелочь.
Это осознанный компромисс, а не однозначная ошибка. Решение — за оператором.

**Ловушка при «исправлении».** Сужение до списка команд легко превращается в видимость
защиты. НЕ включай в NOPASSWD-список:

| команда | почему нельзя |
|---|---|
| `cat`, `less`, `head`, `tail` | с root читают что угодно, включая `/etc/shadow`; у `less` есть побег в оболочку |
| `find` | `-exec` запускает произвольные команды |
| `sqlite3` | встроенная команда `.shell` — прямой путь к root |
| `vi`, `nano`, любые редакторы | из редактора открывается оболочка |
| `apt install`, `dpkg` | установка пакета = выполнение чужого кода от root |
| `systemctl` без указания службы | запуск произвольного юнита = произвольный код |

Безопасный список — только чтение состояния (`ufw status`, `systemctl status`,
`journalctl`, `fail2ban-client status`, `ss`, `sshd -T`, `nginx -t`) и перезапуск
**поимённо перечисленных** служб.

### 9. Группа docker = фактический root (добавлено 2026-07-29)

**Риск:** член группы `docker` может запустить контейнер, смонтировав в него корень
файловой системы хоста, и получить полную власть — sudo для этого не нужен вовсе.
Это не дефект настройки, а свойство Docker: сокет демона работает от root.

**Что проверять:** `getent group docker | cut -d: -f4`

**Зачем в аудите:** без этого пункта оценка защищённости получается завышенной.
Типичная ошибка — закрутить sudo до списка команд, отчитаться об усилении защиты и
не заметить, что рядом осталась открытая дверь. Если пользователь состоит в группе
`docker`, польза от сужения sudo сводится к защите от **случайных** разрушительных
команд (что тоже ценно — это самый частый источник аварий), но не от злоумышленника
с доступом к учётной записи.

**Что делать:** обычно — ничего, но знать и учитывать. Вывод пользователя из группы
ломает всю автоматизацию, работающую с контейнерами (в том числе бэкапы), и цена
почти всегда выше выгоды при одном операторе с одним ключом.

## Docker scope

### 1. daemon.json без insecure-registries

**Риск:** `insecure-registries` отключает TLS-валидацию registry. Это допустимо
для внутреннего registry без TLS, но опасно для публичного — MITM может
подменить образ.

**Допустимое исключение:** внутренний Docker registry в той же приватной сети,
без публичного выхода. Документировать в `inventory/server.md`.

### 2. .env permissions mode 0600

**Риск:** `.env` обычно содержит DB passwords, API tokens. Mode 644 = читаемо
любым пользователем сервера. Если есть второй пользователь (deploy-bot,
sandbox), он читает все секреты.

**Что должно быть:** `chmod 600 .env` — только владелец может читать.

### 3. Внутренние UI на 127.0.0.1

**Риск:** Uptime Kuma, Beszel, Dozzle, Dockge содержат интерфейсы для управления
сервером. Если они открыты на 0.0.0.0 без auth — кто угодно из интернета может
управлять контейнерами.

**Что должно быть:** `127.0.0.1:3001:3001` (bind только на localhost). Доступ
снаружи — через nginx с Basic Auth или WebAuthn.

### 4. Образы pinned

**Риск без pin:** `:latest` тег обновляется silent, при `docker compose up -d`
может прийти новая версия с критичной бага или backdoor (supply chain attack).

**Допустимое исключение:** локальные сборки (контейнеры, собираемые из исходников
проекта в `build:` блоке compose) — `:latest` эквивалентен текущему git-состоянию
исходников. Принцип формализован в ADR 0010 проекта-носителя или эквивалентном
решении.

## Git scope

### 1. gitleaks scan (working tree + history)

**Риск:** оператор случайно закоммитил `.env`, ключ, пароль. Даже если потом
удалил — в git history живёт навсегда (пока не сделан `git filter-repo`).

**Что важно:** скан истории (`--log-opts='--all'`) находит утечки в любом
коммите, не только текущем.

**Что делать при FAIL:** ротировать утёкшие секреты (через `rotate-secrets`),
`git filter-repo` для удаления из истории, force-push в ремоут (если есть).
Force-push в публичный репо — отдельный риск, рассматривать в Yellow Zone.

### 2. .gitignore содержит security patterns

**Риск:** если `.env`, `*.key`, `*.pem`, `secrets/` не в .gitignore — оператор
случайно `git add .` зацепит их.

**Что должно быть:** базовые patterns + специфичные для проекта (например,
`*.tfstate` для Terraform, `node_modules/` стандартно).

## TLS scope

### Сертификат не истекает в ближайшие 14 дней

**Риск:** просроченный сертификат → браузер ругается → пользователи не заходят.

**Что должно быть:** acme.sh обновляет за 30 дней до истечения автоматически
(cron). Аудит проверяет, что cron работает.

**Пороги:**
- < 14 дней: FAIL — что-то сломалось в acme.sh, срочно расследовать.
- 14-30 дней: WARN — приближается срок, но cron должен сработать. Проверь, не
  упал ли cron при последнем обновлении.
- > 30 дней: PASS — нормально.

### Откуда берутся домены и откуда идёт проверка (уточнено 2026-07-29)

**Список доменов — из структуры документа.** Первая колонка markdown-таблицы или
элементы списка; ячейка должна быть доменом целиком. Прежняя версия выбирала домены
регуляркой по всему тексту `domains.md` — и вместе с рабочими забирала всё, что
упомянуто по соседству в прозе: Reality-заглушку, сайт VPN-провайдера, `pypi.org`,
`github.com`. Аудит лез с `openssl` к чужим серверам и вписывал сроки чужих
сертификатов в отчёт оператора.

Это не только мусор: скрипт от имени оператора устанавливал соединения с третьими
лицами, к делу не относящимися. Домены не распознались — честный UNKNOWN, а не
проверка чего попало.

**Проверка идёт с сервера.** `openssl s_client` запускается через ssh на самом
сервере, а не на машине оператора. Причина — записанный урок: на Маке с включённым
TUN-клиентом VPN сетевые проверки описывают путь через туннель, а не состояние
сервера (на этом уже один раз построили ложный вывод о доступности порта). Если на
сервере нет `openssl`, скрипт отступает на локальный прогон и пишет источник в
строку отчёта — разница между «проверено с сервера» и «проверено с Мака» не должна
теряться.

## Что НЕ проверяется (явные out-of-scope)

- **Application-level security** (SQL injection, XSS, CSRF в самом приложении) —
  это ответственность разработчика приложения, не security-аудита инфры.
- **Network-level monitoring** (Wireshark, IDS) — не входит в базовый аудит,
  отдельный продукт.
- **Compliance-frameworks** (PCI-DSS, GDPR audit trails) — отдельная тема, не
  закрывается этим скиллом.
- **Backup-проверка** — отдельный скилл `setup-backups` + check-phase2.sh.

## Рубрика вердиктов: что считать PASS, WARN и FAIL

Раньше это знание жило в прозе: команды были расписаны, а тяжесть отклонения — нет,
кроме срока сертификата. Из-за этого один и тот же результат в разных прогонах получал
разный вердикт, и **отдать проверку постороннему было нельзя** — он не знал порога.
Рубрика чинит именно это: её можно вручить свежему проверяющему вместе с выводом команд,
и вердикт получится тот же самый.

**Правило разделения.** FAIL — дыра, которой можно воспользоваться прямо сейчас, или потеря
доступа. WARN — ослабление защиты без прямой эксплуатации либо срок, который скоро наступит.
NOT_APPLICABLE — проверка неприменима к этому хосту (нет Docker, нет домена); это **не** PASS
и в сводке считается отдельно.

| Проверка | PASS | WARN | FAIL |
|---|---|---|---|
| UFW активен | `Status: active` и default deny incoming | активен, но default allow | неактивен либо не установлен |
| UFW allow-правила | только 22/80/443 или задокументированные исключения | лишний порт, слушает 127.0.0.1 | лишний порт, слушает 0.0.0.0 |
| SSH PasswordAuthentication | `no` | директива отсутствует (зависит от версии сборки) | `yes` |
| SSH PermitRootLogin | `no` или `prohibit-password` | директива отсутствует | `yes` |
| fail2ban | активен, jail `sshd` включён, **бан подтверждён живым тестом** (§3.11) | активен, но живым тестом не проверялся | неактивен либо jail выключен |
| unattended-upgrades | включён, security-only, без авто-перезагрузки | включён с авто-перезагрузкой | выключен |
| Открытые порты | наружу только 22/80/443, остальное на 127.0.0.1 | служебный UI наружу, но за Basic Auth и TLS | БД, панель или админка доступны с 0.0.0.0 |
| daemon.json | нет `insecure-registries` | файла нет (умолчания) | `insecure-registries` задан |
| Права `.env` | `600` у всех | `640` при владельце-группе сервиса | `644` и слабее — читает любой пользователь хоста |
| Внутренние UI | все на 127.0.0.1 | наружу, но под Basic Auth | наружу без аутентификации |
| Теги образов | зафиксированы | `latest` у локальной сборки | `latest` у публичного образа |
| gitleaks | 0 находок в дереве **и** в истории | находки только в `*.example` | живой секрет в дереве или истории |
| `.gitignore` | закрывает `.env`, `*.key`, `*.pem`, `secrets/` | закрывает частично | не закрывает ничего из перечисленного |
