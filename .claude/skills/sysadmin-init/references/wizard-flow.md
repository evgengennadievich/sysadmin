> Это reference для скилла `/sysadmin-init`. SKILL.md ссылается сюда из
> Шагов 2.5, 3, 5, 6 — там оставлены компактные указатели, здесь — полные

## Раунд 1.5 — Проект и путь к папке инфры (`projects[0]` в `agent-config.json`)

> **ADR-0013.** Раньше путь к инфре жил как `infrastructure.root_path` внутри
> единого `sysadmin-config.json`. Теперь это поле реестра проектов в МОЗГЕ:
> `agent-config.projects[0].infra_root` + `default_project`. Конфиг расщеплён на два
> файла — мозг (`agent-config.json` в `sysadmin/`) и карта (`infra-config.json` в папке
> проекта). Этот раунд заполняет запись проекта в мозге.

**Когда задавать:** сразу после Раунда 1 (имя/язык/таймзона), **до** Раунда 2
(менеджер паролей). Без этого ответа все остальные раунды зависают в
воздухе — сервер, мониторинг, бэкапы записываются в `infra-config.json`, но агент не
знает, в какую папку его положить и куда писать `inventory/`, `decisions/`, `knowledge/`.

**1. Контекст простыми словами.**
> «Этот репозиторий (`sysadmin/`) — **мозг агента**: моя персона, скиллы,
> схемы конфигов, шаблон ADR. Он публичный, его клонируют все, кто берёт
> агента себе. Тут же лежит `agent-config.json` — мой паспорт (кто ты, язык,
> твои проекты). А вот **данные** твоей инфраструктуры (карта серверов,
> инциденты, ADR про твой сервер, runbook'и) живут в **отдельной**
> приватной папке, и в ней — `infra-config.json` (карта этого сервера).»

**2. Мини-урок.**
> «Принцип архитектуры — мозг отдельно, данные отдельно. Мозг знает про твои
> проекты через реестр `projects[]`: у каждого проекта свой `id` и `infra_root` —
> путь к его папке. По умолчанию я работаю с проектом из `default_project`. Когда
> тебе нужно «проверь сервер» — я иду в `<infra_root>/inventory/`, «опиши недавний
> инцидент» — `<infra_root>/incidents/`, «что мы решили про бэкапы» —
> `<infra_root>/decisions/`. Реестр в мозге, а не в данных, — поэтому на старте я
> сразу знаю, где всё лежит, без перебора по диску.»

**3. Что заполняем.**

| Поле                 | Пример                         | Заметка |
|----------------------|--------------------------------|---------|
| `projects[0].id`     | `main-server`                  | kebab-case (`^[a-z0-9][a-z0-9-]*$`); сгенерирую из имени, если не предложишь |
| `projects[0].title`  | `Основной сервер Selectel`     | опционально, для удобства |
| `projects[0].infra_root` | `/Users/имя/work/infra`    | путь к папке инфры; **абсолютный предпочтительнее** |
| `default_project`    | `main-server`                  | = id единственного проекта в v1.0 |

**Варианты формата `infra_root`:**

| Формат пути              | Пример                           | Когда выбрать |
|--------------------------|----------------------------------|---------------|
| Абсолютный путь (★)      | `/Users/имя/проекты/моя-инфра`   | Самый надёжный, реестр в мозге не привязан к cwd |
| Полный путь с tilde      | `~/projects/my-infra`            | Инфра живёт где-то в твоих проектах |
| Папка-сосед              | `../infra`                       | `sysadmin/` и `infra/` лежат рядом; резолвится от каталога мозга |

**4. Рекомендация сеньора.**
> «Дай проекту короткое имя (например `main-server`) — если не предложишь, я сделаю
> его из имени сервера. Для `infra_root` лучше абсолютный путь. Если ты только
> склонировал `sysadmin/` и пока не создавал папку инфры — пиши `../infra`, рядом с
> этой папкой; я проверю, что путь либо существует, либо его родитель существует
> (тогда папку создам на шаге записи). Если уже есть готовая папка — указывай реальный
> путь.»

**5. Разрешение довериться.**
> «Если не уверен — пиши «как ты советуешь»: подставлю `id=main-server` и `../infra`
> как папку инфры.»

**6. Открытая дверь.**
> «Подробнее про расщепление конфига и реестр проектов — в ADR-0013
> (`decisions/0013-config-split-brain-vs-infra.md`).»

**Запрос ответа:** через `AskUserQuestion` (text) — id (default из имени сервера),
title (опц.), infra_root (default `../infra`).

**Валидация ответа** (псевдокод):

```bash
RAW_ID="$1"        # id проекта (или пусто → сгенерируем)
RAW_TITLE="$2"     # title (опц.)
ANSWER="$3"        # infra_root, как ввёл оператор

# 0. id: нормализуем в kebab-case; если пусто — генерируем из имени сервера/проекта.
PROJ_ID="$(printf '%s' "$RAW_ID" | tr '[:upper:]' '[:lower:]' | sed -E 's/[^a-z0-9-]+/-/g; s/^-+|-+$//g')"
[ -z "$PROJ_ID" ] && PROJ_ID="main-server"

# 1. Раскрыть tilde и сделать путь абсолютным для проверки
EXPANDED_PATH="${ANSWER/#\~/$HOME}"
if [[ "$EXPANDED_PATH" != /* ]]; then
    # Относительный путь — резолвлю относительно cwd скилла (это будет sysadmin/).
    # Согласовано с resolve_active_project (find-config.sh): infra_root в мозге
    # резолвится от $HOME (tilde) или нормализуется через cd, если папка есть.
    ABS_PATH="$(cd "$(pwd)" && cd "$EXPANDED_PATH" 2>/dev/null && pwd || echo "$PWD/$EXPANDED_PATH")"
else
    ABS_PATH="$EXPANDED_PATH"
fi

# 2. Проверить существование
if [ -d "$ABS_PATH" ]; then
    echo "OK: папка существует ($ABS_PATH). Агент будет читать inventory оттуда."
elif [ -d "$(dirname "$ABS_PATH")" ]; then
    echo "WARN: папки $ABS_PATH нет, но родитель существует."
    echo "Скилл создаст её на шаге записи (mkdir -p)."
elif [ -z "$ANSWER" ]; then
    echo "ERROR: пустой ответ. infra_root обязателен по schema. Повторяю вопрос."
else
    echo "ERROR: ни папка $ABS_PATH, ни её родитель не существуют."
    echo "Уточни путь — может быть опечатка, или родительские папки тоже нужно создать."
fi

# 3. Сохраняю ответы в переменные для Шага 8 SKILL.md (сборка agent-config-draft.json):
#    PROJ_ID, PROJ_TITLE, PROJ_INFRA_ROOT. Запись в draft делает Шаг 8.1.
PROJ_TITLE="$RAW_TITLE"
PROJ_INFRA_ROOT="$ANSWER"   # как ввёл оператор; Шаг 10 нормализует до абсолютного
```

**Важные моменты:**

- `infra_root` на превью записывается **как ввёл оператор** (с tilde — так и пишем).
  На Шаге 10 SKILL.md, после `mkdir -p`, путь нормализуется до **абсолютного** (`cd ... && pwd`)
  — реестр в мозге не должен зависеть от cwd. Cold Start / `resolve_active_project` при
  чтении раскрывают tilde через bash-замену `${RAW/#\~/$HOME}`.
- Если родитель пути существует, но самой папки нет — это нормально, скилл
  не блокирует, оставляет WARN и создаёт папку на Шаге 10. Сценарий: оператор пишет
  `../infra`, а папки пока нет рядом с `sysadmin/`. Это ожидаемая ситуация.
- Если родителя тоже нет — это явная опечатка, повторяю вопрос.

## Раунд 2 — Менеджер паролей (`secrets.manager`)

**1. Контекст.**
> «Менеджер паролей — это где хранить токены, ключи, пароли от серверов
> и сервисов. Это НЕ путать с `.env`-файлами в проекте: `.env` уязвим
> (можно нечаянно закоммитить в git), менеджер паролей — отдельное
> защищённое хранилище.»

**2. Мини-урок.**
> «Принцип нашего проекта — секреты НИКОГДА не лежат в репо, в репо лежат
> только указатели вида „пароль от X — смотри Keychain под именем Y“.
> Это спасает в трёх сценариях: случайный `git push` секрета, утечка
> диска, ротация токена (меняешь в одном месте — все скиллы видят новое
> значение).»

**3. Варианты с плюсами и минусами.**

| Менеджер     | Плюсы                                       | Минусы                                |
|--------------|---------------------------------------------|---------------------------------------|
| `keychain`   | Встроен в macOS, ничего ставить не надо     | Только macOS                          |
| `bitwarden`  | Cross-platform, бесплатно, есть CLI `bw`    | Нужен аккаунт, синхронизация в облаке |
| `1password`  | Удобный UI, командная работа, есть CLI `op` | Платный (~$3/мес)                     |
| `pass`       | Локальный, на gpg, минимум зависимостей     | Только Linux, gpg-ключи руками        |
| `keepassxc`  | Локальная база `.kdbx`, CLI `keepassxc-cli` | База — один файл, бэкапить вручную    |
| `other`      | Любой твой менеджер (Kaspersky и т.п.)      | Если нет CLI — секреты передаёшь руками |

**4. Рекомендация.**
> Если ты на macOS — `keychain` (детект показал OS=`Darwin`): встроенный,
> не требует аккаунта, скиллы агента уже умеют с ним работать через
> `security` CLI. Если на Linux — `pass` (минимум зависимостей) или
> `bitwarden` (если хочешь синхронизацию между машинами).

**5. Разрешение довериться.**
> «Можешь написать „давай как ты советуешь“ — я подставлю рекомендацию
> по твоей OS.»

**6. Открытая дверь.**
> «Подробнее — в `decisions/0008-vault-keychain-by-default.md` (или
> аналогичном ADR в твоей инфре) и `.claude/skills/setup-secrets-vault/SKILL.md`.»

Записываю ответ в `secrets.manager`. Для известных менеджеров
(keychain/bitwarden/1password/pass/keepassxc) дополнительно `cli_available: true`.
Подсказка после: «Реальные значения паролей сюда не пишу — они появятся
в выбранном менеджере, когда запустишь `/setup-secrets-vault`.»

### Ветка «Другой менеджер» (`manager=other`) — research CLI + честный выбор

Если оператор выбрал «Другой» или назвал менеджер вне списка (Kaspersky, Dashlane,
NordPass, браузерный и т.п.):

1. **Спрашиваю имя** → `secrets.manager_name` (напр. «Kaspersky Password Manager»).
2. **Ресёрч через WebSearch:** есть ли CLI у этого менеджера (запрос «<имя> password
   manager CLI command line»). **Не выдумываю** — если достоверно не нашёл, считаю
   «CLI нет/неизвестен» (приоритет №1 CLAUDE.md — запрет на выдумки).
3. **Объясняю расклад честно:**
   - **CLI есть** → «У <имя> есть CLI `<команда>` — смогу доставать секреты сам.
     Пишу `cli_available: true`.»
   - **CLI нет** (Kaspersky, большинство браузерных) → честно: «У <имя> нет CLI, я не
     смогу доставать пароли автоматически. Значит ты будешь сам открывать <имя>,
     копировать пароль и присылать мне — медленно при частых операциях (деплой,
     ротация). Альтернатива — **Bitwarden** (бесплатный, кроссплатформенный, CLI `bw`):
     можешь личное оставить в <имя>, а для инфраструктуры завести Bitwarden, тогда
     я автономен. Решай: (а) остаюсь на <имя>, передаёшь руками — `cli_available: false`;
     (б) перехожу на Bitwarden — `manager=bitwarden`.»
4. **Записываю по выбору:** `manager=other` + `manager_name` + `cli_available`, либо
   `manager=bitwarden` (если согласился перейти).

**Граница (приоритет №1):** не объявляю CLI существующим без подтверждения ресёрчем.
Лучше честное «CLI не нашёл, считаю что его нет», чем ложное обещание автоматизации.

## Раунд 4 — Мониторинг (`monitoring.enabled` + `monitoring.stack`)

**1. Контекст.**
> «Мониторинг — это глаза агента. Без него агент работает реактивно
> (отвечает на твой вопрос „как там сервер?“ через `ssh + docker ps`).
> Со стеком — проактивно: видит ситуацию заранее по UI-панелям и шлёт
> алерты в Telegram, если что-то упало.»

**2. Мини-урок.**
> «В мире мониторинга три слоя: uptime-checks (живой ли сервис), metrics
> (CPU/RAM/диск), logs (что происходит внутри). Большие команды используют
> Prometheus+Grafana, но это overkill для одного-двух серверов. Мы
> используем готовые self-hosted UI: Uptime-Kuma (uptime), Beszel
> (metrics), Dozzle (логи в браузере), Dockge (управление compose-стеками),
> Diun (алерты на обновления Docker-образов).»

**3. Варианты.**

| Вариант      | Что включено                                  | Когда выбрать                            |
|--------------|-----------------------------------------------|------------------------------------------|
| Не ставить   | Ничего                                        | Сервер тестовый, метрики не нужны        |
| Базовый      | uptime-kuma + beszel                          | Один сервер, минимум — uptime + метрики  |
| Полный (★)   | uptime-kuma + beszel + dozzle + dockge + diun | Production-сервер, нужны логи и контроль |

**4. Рекомендация.**
> Для production — полный (★). Базовый теряет логи (придётся
> `ssh + docker logs`) и алерты на устаревшие образы. Полный = ~150 МБ RAM
> на все 5 контейнеров, не накладно.

**5. Разрешение довериться.**
> «Если сервер production — пиши „полный“ или „как советуешь“. Если
> тестовый — „не ставить“.»

**6. Открытая дверь.**
> «Подробнее в `.claude/skills/install-monitoring-stack/SKILL.md` — там
> описан процесс установки и конфигурация Basic Auth для общей панели.»

Если выбрал «полный» или «базовый» → записываю `monitoring.enabled = true`
и `monitoring.stack`. Если включён → спрашиваю `panel_domain` (поддомен
для админ-панели, например `sysadmin.example.com`). Валидация: формат
hostname (regex `^[a-z0-9.-]+$`).

## Раунд 5 — Бэкапы (`backups.enabled` + `backups.destination`)

**1. Контекст.**
> «Бэкап — единственная страховка от твоих и моих ошибок. Без бэкапа
> любая правка БД, любое обновление Docker-образа, любой `rm -rf` —
> лотерея. С бэкапом — можно откатиться за 5-10 минут.»

**2. Мини-урок.**
> «Хороший бэкап удовлетворяет правилу 3-2-1: три копии данных, на двух
> разных носителях, одна — offsite (вне твоего сервера). Мы используем
> `restic` — современный backup-tool с шифрованием и инкрементальными
> снапшотами. Куда складывать — выбор destination'а ниже.»

**3. Варианты destination.**

| Destination          | Плюсы                                          | Минусы                          |
|----------------------|------------------------------------------------|---------------------------------|
| `yandex-disk-webdav` | Бесплатно до 1 ТБ, для русскоязычных доступнее | Нужен rclone, чуть медленнее    |
| `s3`                 | Надёжнее всего, неограниченный объём           | Платно (~$0.02/ГБ/мес AWS)      |
| `b2` (Backblaze)     | Дешевле S3 в 4 раза, тот же API                | Меньшая распространённость      |
| `nextcloud-webdav`   | Свой self-hosted (полный контроль)             | Сам поднимаешь Nextcloud-сервер |
| `local`              | Бэкап на тот же хост (быстро, бесплатно)       | НЕ offsite, теряешь при пожаре  |

**4. Рекомендация.**
> Для русскоязычного оператора с одним production-сервером —
> `yandex-disk-webdav`: 1 ТБ бесплатно, через rclone работает прозрачно,
> restic шифрует данные перед загрузкой. Если объём > 1 ТБ или нужна
> международная инфра — `s3`/`b2`. `local` — НЕ выбирай: при отказе диска
> теряешь и данные, и бэкап одновременно.

**5. Разрешение довериться.**
> «Если в России и один сервер — пиши „yandex-disk-webdav“ или „как
> советуешь“.»

**6. Открытая дверь.**
> «Подробнее в `.claude/skills/setup-backups/SKILL.md` и ADR
> `decisions/0009-restic-yandex-webdav.md` (или эквивалент в твоей инфре).»

Если включил → спрашиваю:
- `backups.destination` (radio из enum схемы).
- `backups.rclone_remote` (если destination — webdav-вариант): имя
  remote'а в `~/.config/rclone/rclone.conf` (например `yandex-disk`).
  Валидация: regex `^[a-zA-Z][a-zA-Z0-9_-]+$`.
- `backups.retention` (text, default `7d-4w-6m` — 7 дней, 4 недели,
  6 месяцев). Подсказка: «Стандарт индустрии. Можешь оставить или ввести
  свой формат `Nd-Nw-Nm-Ny`.»

# Операционные детали раундов (поля, enum, regex, дефолты)

Эта секция — точные значения, которые уходят в конфиг: какие поля, какие enum'ы, какие
regex-проверки, что по умолчанию. Разделы выше объясняют, **как разговаривать** с оператором;
здесь — **что записать** по итогам разговора.

Открывать вместе с таблицей раундов из `SKILL.md`, Шаги 2–7.5.

**Раунд 1.5 (проект + путь к инфре).** Дефолт `infra_root` — `../infra` (сосед `sysadmin/`),
лучше абсолютный путь. `id` нормализую в kebab-case (regex `^[a-z0-9][a-z0-9-]*$`); если
родителя пути нет — повторяю вопрос (опечатка). `default_project = projects[0].id` (v1.0 —
один проект). Записываю `infra_root` как ввёл оператор (резолвер раскроет tilde).

**Раунд 2 (менеджер паролей).** Enum `keychain`/`bitwarden`/`1password`/`pass`/`keepassxc`/
`other`; дефолт по OS (macOS→`keychain`, Linux→`pass`). Для известных — `cli_available:true`.
Ветка **«Другой менеджер»** (research CLI + честный выбор «остаться руками / перейти на
Bitwarden») — полностью в разделе «Раунд 2» этого же документа, подраздел «Другой менеджер»; пишу `manager_name` +
`cli_available` по результату ресёрча. Подсказка: реальные значения — не сюда, а в
`/setup-secrets-vault`.

**Раунд 3 (сервер).** Если `ssh_aliases` в `detect-defaults.json` непуст — выбор из
найденных (radio), иначе спрашиваю вручную. `role`: `production`/`staging`/`test`/`personal`.
**v1.0 — один сервер**; про второй: «добавишь вручную в `servers[]`, схема разрешает массив
≥1» (см. `references/edge-cases.md`).

**Раунд 4 (мониторинг).** `enabled` → при включении `stack` (массив из enum) и
`panel_domain` (hostname, regex `^[a-z0-9.-]+$`). Варианты: не ставить / базовый
(uptime-kuma+beszel) / полный (+dozzle+dockge+diun, ★ для production).

**Раунд 5 (бэкапы).** `enabled` → `destination` (enum: `yandex-disk-webdav` для РФ /
`s3`/`b2` / `nextcloud-webdav` / `local`(не советую)), `rclone_remote` (для webdav-вариантов,
regex `^[a-zA-Z][a-zA-Z0-9_-]+$`), `retention`. **⚠️ `retention` — ОБЪЕКТ `{daily,weekly,
monthly}` (целые), НЕ строка** (схема `additionalProperties:false`). Дефолт `{daily:7,
weekly:4,monthly:6}` (можно описать как «7д-4н-6м», но в конфиг пишется объектом).

**Раунд 6 (Telegram).** `enabled` → `bot_username` (без `@`, regex
`^[a-zA-Z][a-zA-Z0-9_]{4,31}$`; создать через @BotFather), `chat_type` (`personal`/`channel`).
Реальный токен — в менеджер паролей, не сюда.

**Раунд 6.5 (VPN).** Заготовка секции под VPN-скиллы. Если включил: `vpn.enabled=false`,
`panel_url=null`, `panel_web_base_path=null`, `server_proxy_enabled=false`,
`upstream_kind="none"`, `default_reality_dest="www.cloudflare.com"`. Конкретные значения
впишет `/setup-vpn-panel`. Не включил — секция не добавляется (попросят
`--reconfigure` при первом `/setup-vpn-panel`).
