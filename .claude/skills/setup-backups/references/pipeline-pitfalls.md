# Грабли конвейера бэкапа (не самого restic)

Справка к скиллу `/setup-backups`. Здесь — ошибки в **обвязке**: скриптах дампа,
оркестраторе, cron-окружении, алертах, уборке за хранилищем. Грабли самого restic
(хранилища, forget/prune, passphrase, производительность) — в `restic-quirks.md`.
Порядок восстановления PostgreSQL — в `pg-restore-order.md`.

Открывать, когда бэкап настроен, но ведёт себя не так, как обещает процедура.

---

## Самая дорогая: `source` конфига без `set -a`

**Симптом:** дампы БД проходят с `SUCCESS`, а `restic backup` падает с
`Fatal: Please specify repository location`.

**Причина:** `source /root/.backup-env` кладёт переменные в текущий shell, но `restic` и
`rclone` — **дочерние процессы**. Без экспорта они не наследуют `RESTIC_REPOSITORY`,
`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`.

**Лечение:** скрипты оборачивают `source` в `set -a … set +a`.

**Коварство (боевой кейс 2026-07-09).** Ручной e2e-restore-тест это НЕ ловит: оператор
экспортирует переменные руками перед вызовом restic, и баг маскируется. Всплывает он
только на автономном cron-прогоне. **Отсюда требование Шага 7** — гнать restore-тест
через сам `backup-all.sh`, а не в обход него. Это ровно тот случай, когда «зелёный
статус» не доказывает работу (§3.11 персоны).

---

## Скрипты дампа и оркестратор

**`pg_dump` с хоста** — несовместимость версий клиента (хост) и сервера (контейнер) ломает
дамп. ВСЕГДА `docker exec <container> pg_dumpall`: внутри контейнера версии совпадают
гарантированно.

**`backup-all.sh` с `set -e`** — одна упавшая БД останавливает весь прогон, остальные не
бэкапятся. Для оркестратора `set -e` отключён намеренно, достаточно `set -uo pipefail`.

**Redis: `SAVE` вместо `BGSAVE`** — `redis-cli SAVE` блокирует базу на больших датасетах,
минутами. Правильно: `BGSAVE`, потом копия `dump.rdb`.

**Запуск без конфига инфры (`infra-config.json`)** — раньше скилл требовал десяток
CLI-параметров, и оператор не помнил, какие обязательные. Урок: скилл не угадывает
намерения. Нет конфига — `exit 1` с указанием на `/sysadmin-init`;
`backups.enabled=false` — `exit 0` с указанием на `/sysadmin-init --reconfigure`.

## Алерты

**`curl` к алерт-каналу без таймаута.** Реальный кейс: с одного IP `api.telegram.org`
отвечает, с соседнего — timeout (сегмент или DPI). Скрипт висит НАВСЕГДА, а ежедневный
cron копит зависшие процессы. Лечение (2026-07-09): всем `curl` в скриптах скилла добавлен
`-m 20`. Недоступный канал = WARNING в лог и работа дальше, а не зависание.

---

## Уборка за хранилищем

**Огрызки multipart в S3-совместимом хранилище — не бесплатны и не видны.** Провайдер
складывает фрагменты оборванных загрузок в скрытый служебный контейнер
`*_s3multipartuploads` и **тарифицирует** его. Боевой кейс 2026-07-09: 233 МБ мусора,
накопленного за месяц; известный чужой кейс — 551 ГБ.

`rclone cleanup` через штатный `ListMultipartUploads` их может НЕ видеть. Тогда чистить
содержимое служебного контейнера напрямую:

```bash
rclone delete <remote>:<bucket>_s3multipartuploads
```

В cron-шаблон скилла еженедельная чистка уже добавлена.

**`passphrase` в env-файле без `chmod 600`** — любой пользователь с правом чтения получает
ключ к расшифровке всех бэкапов. `chmod 600 /root/.backup-env` обязателен.

## Граничные случаи, которых нет в других справочниках

**Большие БД (>5 ГБ).** `pg_dump` может занимать больше часа — окно cron имеет смысл
сдвинуть на 02:00 или 01:00. Плюс `--ignore-inode` в `restic backup` (подробности —
`restic-quirks.md`).

**БД на отдельной машине или managed** (AWS RDS, Yandex Managed Postgres, Google Cloud SQL,
Supabase и подобные) — **этот скилл не покрывает**. Нужен другой подход: либо managed
snapshots провайдера, либо отдельный backup-узел с доступом к БД через приватную сеть.
Честно сказать это оператору, а не изображать настройку.

**Хранилище без публичного IP** (S3-API через приватную сеть) — нужен endpoint override
в `RESTIC_REPOSITORY`, а при доступе без учётных данных — флаг `--insecure-no-password`.
Форма URL для каждого типа хранилища — в `restic-quirks.md`, раздел «Хранилища».

## Restore-тест на свежем сервере, где БД ещё нет

Боевой кейс 2026-07-09: бэкапы настраивались сразу после первичной настройки сервера,
то есть ДО переноса данных. Восстанавливать нечего — но конвейер всё равно обязан быть
проверен целиком, иначе Шаг 7 превращается в формальность.

Процедура на синтетике:

1. **Поднять тестовый контейнер** образом, который станет продовым (для кластера с
   pgvector — `pgvector/pgvector:pg16`, не чистый postgres). Создать базу с известным
   числом строк: `INSERT … SELECT … FROM generate_series(1,1234)`.
2. **Прогнать оркестратор целиком** — `backup-all.sh`, читающий тот же `/root/.backup-env`,
   что и cron. Не отдельный `backup-postgres.sh`! Только полный прогон воспроизводит
   cron-окружение и ловит баг экспорта конфига (см. раздел про `set -a` выше) — вызов
   restic вручную с экспортированными переменными его маскирует.
3. **Restore во второй контейнер** и сверка row counts с первым.
4. **Уборка:** оба контейнера удалить, `restic forget --tag e2e-test --prune` (тестовый
   snapshot не должен жить в боевом репозитории), локальные дампы стереть. В env-конфиге
   список контейнеров оставить ПУСТЫМ с пометкой «заполнить при переносе БД».

**Грабля ожидания.** `pg_isready` отвечает успехом и на ВРЕМЕННЫЙ сервер initdb: entrypoint
образа запускает его, а потом перезапускает. После первого успеха подождать 5–10 секунд и
проверить повторно, иначе `createdb` попадает в щель рестарта и падает с «socket … failed».

## Restore MySQL и Redis — отдельного справочника нет

Пошаговый справочник написан только для PostgreSQL (`pg-restore-order.md`), потому что
именно там порядок неочевиден (globals → createdb → pg_restore). Для двух других:

- **MySQL / MariaDB** — дамп заливается в поднятый контейнер той же версии
  (`docker exec -i <container> mysql -u root -p<pass> <db> < dump.sql`). Порядок ролей
  отдельным шагом не нужен: пользователи лежат в системной базе `mysql`, и если дамп
  снят с её включением — восстанавливаются вместе.
- **Redis** — восстановление не командой, а файлом: контейнер останавливается, `dump.rdb`
  кладётся в его каталог данных, контейнер поднимается. Загрузка дампа в работающий
  экземпляр не предусмотрена.

Проверка та же, что у PostgreSQL: сверка числа записей (`SELECT count(*)` / `DBSIZE`)
с боевым экземпляром. Тонкости конкретных версий здесь не описаны — если прогон упрётся
в незнакомое поведение, честно сказать оператору «не проверял», а не додумывать.
