# Что лежит в снимке и как читать типы хоста

Справка к скиллу `inventory-scan`. Открывать, когда нужно понять, **какой файл снимка
отвечает на вопрос** — при заполнении inventory-документов, при разборе drift'а или когда
секция оказалась пустой и надо решить, это «нет данных» или «нечего показывать».

Процедура сбора — в `SKILL.md`, Шаг 2. Здесь только состав и семантика.

---

## Что собирает `dump-snapshot.sh`

Сбор идёт через single-shot SSH с timeout 10 с. Каждая секция — отдельный файл в
`inventory/hosts/<host>/snapshots/<DATE>/`.

| Файл снимка | Что внутри |
|---|---|
| `containers.txt`, `containers-inspect.json` | список и полный `inspect` контейнеров |
| `compose-files.txt` | найденные на хосте compose-файлы |
| `networks.txt`, `volumes.txt` | Docker-сети и тома |
| `host-resources.txt` | uptime, память, диск, открытые порты, доступные APT-обновления |
| `crontab.txt` | crontab root (через `sudo -n`) + crontab SSH-пользователя |
| `cron-d-content.txt` | содержимое `/etc/cron.d/*` |
| `nginx-sites.txt` | конфигурация nginx целиком через `nginx -T` |
| `tls-certs.txt` | **даты валидности** через `openssl x509`; главный источник — фактические пути `ssl_certificate` из `nginx -T`, плюс letsencrypt и acme.sh (включая `/root/.acme.sh` через `sudo -n`) |
| `host-scripts-list.txt` | список host-скриптов: `/opt` до 4 уровней без node_modules/venv |
| `host-scripts-content.txt` | содержимое верхнеуровневых `/opt/*.sh`; глубокие IaC-скрипты живут в git, их содержимое в снимок не тянем |
| `host-services.txt` | хост-сервисы вне Docker: нештатные systemd-юниты с Description/User/ExecStart и состоянием — источник секции «Хост-сервисы» в `services.md` |
| `host-env-redacted.txt` | структура `.env`-файлов на хосте: имена переменных, значения замаскированы |
| `systemd-enabled.txt` | включённые systemd-юниты |
| `systemd-timers.txt` | systemd-таймеры оператора — на Ubuntu 24.04 это расписание наравне с cron |
| `watchers.txt` | скрипты-наблюдатели: долгоживущие процессы inotify/fswatch/watchmedo, слушающие события, а не запускаемые по расписанию |
| `firewall.txt` | правила firewall хоста |
| `health-flags.txt` | готовая сводка здоровья: swap%, disk%, loadavg, exited-контейнеры, OOM-коды 137, число отложенных apt/security-обновлений |
| `meta.txt` | метаданные снимка: дата, `host_kind`, метки редакции секретов |
| `<label>.stderr.log` | появляется рядом с секцией, если удалённая команда что-то написала в stderr (ADR-0009). Нормальный продукт скана, не сбой |

**Сводка здоровья подаётся из `health-flags.txt` готовой** — грепать сырьё руками не надо,
скрипт уже посчитал.

## Три типа хоста (`host_kind` в `meta.txt`, ADR-0024)

| `host_kind` | Что значит | Секции контейнеров |
|---|---|---|
| `docker` | Docker есть, демон отвечает | собраны |
| `native` | Docker не установлен | `NOT_APPLICABLE: …` — контейнеров нет как класса |
| `docker-down` | CLI есть, демон не отвечает | `NOT_APPLICABLE: …` — состояние НЕИЗВЕСТНО |

**Разница `native` и `docker-down` принципиальна:** в первом случае «контейнеров нет» —
факт, во втором — слепая зона. `docker-down` на боевом хосте упоминаю оператору как
проблему (служба docker лежит), а не как особенность инвентаря.

От типа хоста зависят две вещи: набор ключевых файлов при verify (Шаг 2) и то, что
писать в inventory-документы (Шаг 4).

### Нативный хост — чем заполняются документы

- **`services.md`** строю **целиком** из `host-services.txt` + `systemd-enabled.txt` +
  портов из `host-resources.txt`. Секция контейнеров — не пустая заглушка, а честная
  строка «Docker на хосте не установлен — сервисы работают нативно (systemd)».
- **`networks.md` / `volumes.md`**: вместо Docker-сущностей описываю сетевую картину
  хоста — слушающие порты (`ss`), правила firewall (`firewall.txt`), какие адреса наружу.
  Пустой документ не оставляю: «нет данных» и «нечего показывать» — разные вещи (C.2).
- **`host_kind=docker-down`** — **не** пишу «контейнеров нет». Пишу «состояние
  контейнеров снять не удалось: демон Docker не отвечает», прежние записи о контейнерах
  НЕ удаляю и поднимаю оператору как проблему хоста, а не как факт инвентаря.

## `automations.md` — сводная витрина

Генерируется только при наличии хоть одной автоматизации. Это «оглавление всего, что
работает само». Колонки: `name | trigger | schedule | runs | touches | log | status`.

Агрегируется из четырёх источников снимка:

| Источник | Значение `trigger` | Откуда расписание |
|---|---|---|
| `crontab.txt` / `cron-d-content.txt` | `cron` | из строки crontab |
| `systemd-timers.txt` | `systemd-timer` | из `list-timers`; что запускается — из парного `*.service` юнита |
| `watchers.txt` | `watcher` | расписания нет — событие |
| `host-scripts-content.txt` | — | чем pipeline/скрипт занят (для колонки `touches`) |

**Колонка `touches` — главная:** что автоматизация трогает (БД из `databases.md`, сервис
из `services.md`, внешний API — Telegram/RSS/Claude). Это источник связей для сборщика
дашборда (ADR-0019).

Не дублирую `cron.md` / `host-scripts.md` слово в слово — агрегирую и осмысляю.
Автоматизаций на сервере нет — документ не создаю.
