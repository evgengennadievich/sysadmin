# 03 — Петли проверки в Claude Code через скиллы

**Источник:** https://claude.com/blog/building-verification-loops-in-claude-code-with-skills
**Дата:** 2026-07-22

## Что такое петля проверки

Повторяющийся цикл, в котором агент **сам проверяет свою работу** — гоняет тесты, линтеры
или собственные проверки — и чинит найденное до того, как двинуться дальше.

Ключевая мысль: агент останавливается, когда работа **выглядит** сделанной. Если у него нет
проверки, которую можно запустить, «выглядит сделанной» — единственный доступный сигнал,
и **петлёй проверки становится человек**: каждая ошибка ждёт, пока её заметит оператор.

> Это дословно совпадает с нашим рефлексом §3.11 («зелёный статус не доказательство»),
> выведенным из ожогов: `fail2ban active` и не ловит, `healthy` при убитом процессе,
> coach-bot 6,5 часов глухой при зелёном healthcheck.

## Как выглядит проверка

Годится всё, что возвращает читаемый агентом сигнал «прошло / не прошло»: набор тестов,
код возврата сборки, линтер, скрипт, сравнивающий вывод с эталоном, скриншот браузера
против макета.

**Требование к отчёту:** агент должен показывать **доказательство**, а не утверждать успех —
вывод теста, саму команду и что она вернула, скриншот результата. Читать доказательство
быстрее, чем перепроверять работу самому, и это работает для сессий, за которыми не следили.

## Насколько жёстко проверка держит остановку

Четыре уровня, от дешёвого к надёжному:

| Уровень | Как | Что даёт |
|---|---|---|
| В одном запросе | «сделай и прогони проверку в этом же сообщении» | работает сразу, ничего настраивать не надо |
| На всю сессию | условие `/goal` — отдельный оценщик перечитывает его после каждого хода | агент работает, пока условие не выполнено |
| Детерминированный шлюз | **Stop-хук** запускает проверку скриптом и не даёт закончить ход, пока не пройдёт | не зависит от решения модели |
| Второе мнение | верифицирующий субагент со свежим контекстом, которому дают опровергнуть результат | проверяет не тот, кто делал |

Отмечено ограничение: Claude Code перебивает Stop-хук и завершает ход после **8 подряд**
блокировок. То есть хук — не вечный замок, а сильный ограничитель.

> У нас Stop-хук уже используется: `inventory-sync-guard.sh` (ADR-0023) не даёт завершить
> ответ, если менял инфраструктуру и не тронул inventory.

## Пример скилла-проверки

```markdown
# .claude/skills/verify-log-hygiene/SKILL.md
---
name: verify-log-hygiene
description: Check that error logs include the request ID and never
  include the request body. Use when the diff touches error handling
  or logging.
allowed-tools: [Read, Edit, Grep]
---
Read the error-handling paths in the current diff.

For each log call on an error path, confirm it includes the request ID
and does not pass the request body, headers, or any user-supplied payload.

Report each violation with file:line, then fix it: add the request ID
where it's missing and strip the payload from the log call.
```

Обрати внимание: тело скилла — **процедура из трёх шагов**, не эссе. Ровно то, что
подтверждают замеры в [конспекте 02](02-skills-empirics-skillsbench.md).

## Четыре способа подключить проверку

1. **Отдельно** — зовёшь вручную после того, как артефакт готов. Для сквозных редких
   проверок: аудит безопасности, доступность, лицензии. Признак, что пора повышать
   уровень: ты и так гоняешь её после каждого изменения.
2. **Встроенно** — проверка дописана в конец скилла, который производит результат.
   Работает только для скиллов, которые ты контролируешь.
3. **Цепочкой** — один скилл вызывает другой. Так добавляется проверка к скиллу, который
   править нельзя. Плата — больше токенов, надо обкатывать до широкого включения.
4. **Шлюзом на PR** — когда цепочка устоялась, та же процедура применяется ко всем
   изменениям автоматически. Проверка переезжает из личной привычки в общую инфраструктуру.

## Как находить кандидатов

Смотри, какую **ручную правку ты делаешь после агента чаще всего**. Если ты каждый раз
вносишь одну и ту же мелкую поправку — эту поправку пора превращать в проверку.
Формулировать сначала простым текстом, как объяснил бы новому сотруднику, включая
и качественные критерии, и жёсткие правила («отклоняй миграцию, которая удаляет колонку
без шага переноса данных»).
